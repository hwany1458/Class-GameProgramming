# Gem Hunter Match 기반 게임 제작 강의자료

Nov 17, 2026 · @YongHwan Lee

공통 프로세스 강의노트 템플릿의 《 》를 Unity 공식 2D URP 샘플 Gem Hunter Match 기준으로 채운 게임별 강의자료다. Happy Harvest 강의자료와 같은 구성이며, 공통 본문(학습 목표·방법론·양식)은 템플릿을 그대로 쓴다.

## 0. 게임 개요와 강의 설계

Gem Hunter Match는 Unity가 2024년 4월 공개한 2D 매치-3 퍼즐 샘플로, 바다속 보석·불가사리·거북이를 세 개 이상 맞춰 지우는 3개 레벨과 레벨 선택·상점·하트(라이프)·코인·별 같은 메타 요소의 골격까지 갖추고 있다. Happy Harvest와 달리 "게임의 틀"은 이미 있고 내용물(레벨 수·특수 조합·진행 저장)이 얕다. 개발자가 "그래픽 데모 목적이며 게임플레이 QA는 충분히 하지 않았다"고 밝혔고 포럼에 보드 로직 버그가 보고되어 있어, "버그 분석·수정"이 수업 소재가 된다는 점이 이 게임의 특징이다.

## 1. 0주차 — 강사 사전 준비

이 게임은 보드 로직이 Board.cs 한 파일에 몰려 있어(포럼 보고 기준 1,000줄 이상), 강사가 먼저 그 파일의 "지도"를 만들어 두지 않으면 학생이 길을 잃는다.

- [ ] Unity 6.3 LTS 설치, Gem Hunter Match 1.6 임포트(새 2D URP 프로젝트 → Package Manager > My Assets) → 설정 변경 팝업 수락 → 콘솔 경고 캐플처
- [ ] Unity 6 필수 수정: TileShader(Shader Graph)의 NormalMap 속성을 Global → Per Material로 변경 후 저장. 이 절차를 스크린샷으로 설치 절차서에 포함(학생 1주차 첫 실습)
- [ ] 레벨 3개 모두 클리어·실패해 보고 상점 화면까지 확인. 포럼에 "상점이 동작하지 않는다"는 보고가 있으므로 현 버전에서 구매가 실제로 반영되는지 기록
- [ ] 버그 재현 시도: 레벨의 젬 종류 수를 3으로 낮추고 폭탄·로켓을 빠르게 연속 스와프 → 낙하 멈춤 또는 `Board.TickSwap` NullReference 재현 여부 기록(3단계 도전 과제의 재료)
- [ ] Board.cs 지도 작성: 메서드를 "입력 처리 / 매치 판정 / 제거·보너스 생성 / 낙하·보충 / 목표·종료 판정 / 연출·VFX 호출" 6개 구역으로 묶은 표 — 학생에게 배포하는 유일한 "정답 일부"
- [ ] `Data` 폴더 인벤토리: LevelList, 레벨 에셋, BonusItems, ShopItems, 젬 정의 에셋의 필드를 표로 정리(2단계 "데이터만으로 되는 기능" 판단 근거)
- [ ] 강사 시범 구현(4번 섹션: 새 레벨 1개 추가)을 끝까지 수행하고 레벨 저작 절차를 스크린샷으로 기록
- [ ] WebGL 빌드 1회: 용량·로딩 측정, Sprite Custom Lit·Radial Warp가 브라우저에서 렌더되는지 확인, 터치 입력 동작 여부 확인(모바일 테스트를 개발자가 권장)
- [ ] 템플릿 Git 저장소(비공개): 임포트 + Unity 6 셰이더 수정 직후 상태를 초기 커밋, `.gitignore`, Git LFS, Force Text
- [ ] 학생 계정 과제 공지: Unity ID, GitHub, itch.io

**실습실 요구사항**: Happy Harvest보다 가볍다. 다만 Sprite Custom Lit·Radial Warp 때문에 셰이더 컴파일이 첫 실행 시 수 분 걸릴 수 있으므로 수업 전 프로젝트를 한 번 열어 두게 한다.

## 2. 1단계 분석 (1주) — 기능분해 → 소스분석 → 현황 파악

Gem Hunter Match 분석의 열쇠는 "보드는 상태 기계"라는 점이다. 한 번의 스와프가 즉시 끝나지 않고 여러 프레임에 걸쳐 "스와프 중 → 매치 처리 → 낙하 중 → 보충 → 안정" 상태를 거치며, 포럼의 버그는 모두 이 상태 전이가 빠른 입력에 꾸여서 생긴다. 학생이 이 상태 흐름을 그릴 수 있으면 버그도, 확장도 보인다.

**기능분해표 초안 (강사 정답본 골격 — 학생에게는 대분류까지만 개방)**

| 대분류 | 기능 | 세부 동작 | 담당 씬/오브젝트 | 담당 스크립트·데이터 (0주차에 확정) | 현황 |
| --- | --- | --- | --- | --- | --- |
| 코어 루프 | 스와프 입력 | 클릭/드래그로 인접 칸 교환, 매치 없으면 되돌림 | 레벨 씬 Board | Board(입력 구역), Input System | ● (터치 동작 확인 필요) |
| 코어 루프 | 매치 판정 | 가로·세로 3+ 탐색, 4·5·L·T 조합 식별 | — | Board(판정 구역) | ● |
| 코어 루프 | 제거·보너스 생성 | 매치 젬 제거, 조합 모양에 따라 부스터(폭탄·로켓 등) 생성, 코인 지급 | — | Board, BonusItems 프리팹(조합 모양 파라미터) | ● |
| 코어 루프 | 낙하·보충 | 빈 칸 위 젬 낙하, 최상단 새 젬 생성, 연쇄 재판정 | — | Board(낙하 구역), Gem | ✕ (빠른 스와프 + 폭탄 시 낙하 멈춤·NullReference — 포럼 보고, 현 버전 확인) |
| 코어 루프 | 블로커 | 나무상자: 인접 매치로 제거 / 밧줄: 아래 매치로 제거 | 레벨 씬 | Board, 블로커 정의 에셋 | ● (2종뿐) |
| 코어 루프 | 목표·이동 횟수·승패 | 목표 요소 카운트, 달성 시 승리, 실패 시 하트 차감 | 레벨 씬 Goals UI | 레벨 데이터 에셋, UI 핸들러 | ● |
| 콘텐츠 | 레벨 3개 | 젬 종류 수·목표·보드 모양 | 레벨 씬 × 3 | LevelList SO → 레벨 참조 | ◐ (3개, 레벨 에디터 없음) |
| 콘텐츠 | 젬 6종·부스터 | 진주·사파이어·불가사리·물고기·조개·거북이, 부스터 프리팹 | — | 젬 정의 에셋, Data/BonusItems | ● |
| 시스템 | 레벨 선택 | Main 씬에서 레벨 목록 표시·진입 | Main 씬 | LevelList SO | ● (잠금·별점 없음) |
| 시스템 | 상점·재화 | 코인으로 하트·부스터 구매, 별 수집 | 레벨 종료 후 상점 UI | Data/ShopItems, 인벤토리 | ◐ (동작 미확인 보고, 코인·별의 사용처 없음) |
| 시스템 | 진행 저장 | 코인·하트·클리어 여부 영속화 | — | (0주차 확인) | ○/◐ |
| UI·연출 | 셰이더·라이트·효과 | Sprite Custom Lit 반짝임, Lights 프리팹, LightRotator, Radial Warp 충격파 | 레벨 씬 | TileShader, Radial Warp, LightRotator | ● (분석 범위 밖) |
| 메타·진행 | 점수·콤보·별점·힌트·하트 회복 | — | — | — | ○ 없음 |

**소스분석 경로 (강사 시범 + 학생 반복)**

1. 진입점: Main 씬이 LevelList를 읽어 버튼을 만들고 레벨 씬을 로드하는 경로, 레벨 씬에서 Board가 초기 보드를 채우는 순서(초기 매치가 없도록 보장하는가?)
2. 스와프 1회의 여정: 입력 → 셀 좌표 → 교환 연출 시작 → (프레임 경과) `Board.TickSwap` → 매치 판정 → 제거·보너스 → 낙하 틱 → 보충 → 재판정 → 안정. 각 단계가 Update의 어느 분기에서 돌아가는지 표시한 **상태 전이도**가 이 게임 소스 분석서의 핵심 산출물(Happy Harvest의 호출 흐름 다이어그램에 해당)
3. 데이터와 로직 분리: `Data` 폴더 에셋의 필드표 — 젬 정의, 부스터의 조합 모양, 상점 아이템 가격, 레벨의 목표·젬 종류 수. "Assets > Create > 2D Match" 메뉴로 무엇을 만들 수 있는지가 곰 데이터 확장의 범위
4. Board.cs 지도(0주차 작성) 위에 학생이 직접 메서드를 배치해 보는 실습 — "이 메서드는 6개 구역 중 어디인가"
5. 버그 재현 실습: 포럼 보고된 재현 절차로 낙하 멈춤을 만들고, 어느 상태에서 멈추는지 디버거로 확인 — 현황 보고서의 ✕ 항목에 재현 단계와 호출 스택 스크린샷 첨부

**일부러 비어 있는 곳**: 레벨 3개 · 코인·별의 쓰임새 없음(상점은 골격만) · 점수·콤보·별점 없음 · 레벨 잠금·진행 저장 불확실 · 힌트·셔플(가능한 수가 없을 때) 없음 · 블로커 2종뿐

**분석 제외 영역**: TileShader·Radial Warp 내부, 노멀·마스크 맵 제작, LightRotator의 라이팅 수학 — "어떤 효과인지 말할 수 있으면 충분, 수정하지 않는다"

**점검 질문 (Gem Hunter Match 전용)**: 스와프 후 매치가 없으면 누가 되돌리는가? 낙하가 끝났다는 것을 보드는 어떻게 아는가? 새 젬 종류를 추가하려면 코드를 고쳐야 하는가, 에셋만 추가하면 되는가? 보드 모양은 어디에 정의되는가?

## 3. 2단계 설계 (1주) — 추가 기능 도출 → 구현 방향과 가이드

Gem Hunter Match는 "틀은 있고 살이 없다" — 상점·코인·하트가 있지만 서로 연결되지 않고, 레벨이 3개뿐이다. 그래서 후보는 "있는 것을 이어 붙이는 기능"과 "콘텐츠를 늘리는 기능"으로 나뉘고, 여기에 이 게임만의 세 번째 갈래인 "기존 버그 수정"이 더해진다. 장르 관습 레퍼런스: 캣디 크러시 사가(목표·이동 횟수·별점·라이프), 로얄 매치(힌트·콤보 피드백).

**강사 제시 기능 후보 10개와 2×2 분류**

| # | 기능 (사용자 스토리) | 가치 | 난이도 | 분류 | 확장 방식 |
| --- | --- | --- | --- | --- | --- |
| 1 | 새 레벨 1개 — 플레이어는 레벨 4를 선택해 새 목표·새 보드 모양으로 플레이한다 | 중 | 하 | 시범 구현 | 레벨 씬 복제 + 레벨 데이터 에셋 + LevelList 등록 (코드 변경 0) |
| 2 | 점수·별점 결과 화면 — 매치마다 점수가 오르고, 클리어 시 남은 이동 횟수에 따라 1\~3별이 표시된다 | 상 | 하 | 필수 | 제거 이벤트 구독 + 점수 클래스 + 결과 UI 패널 (Board 내부 변경 최소) |

권장 조합: **필수 = 점수·별점(2) + 레벨 잠금·저장(3)**, **도전 = 힌트(5) 또는 상점 연결(4)** — 필수 둘만 해도 "레벨 깨고 별 받고 다음 레벨 열기"의 진행 루프가 생긴다. 상위 팀에게만 버그 수정(8)을 도전으로 허용 — "남의 버그를 고치는 경험"이 가장 실무에 가깝지만 실패 위험도 크다. 새 레벨 추가(1)는 시범 따라하기로 모두 수행.

**이 게임이 유도하는 확장 방식**: ① 레벨·젬·부스터·상점 아이템은 "Assets > Create > 2D Match" 데이터 추가로 ② 점수·진행·힌트는 Board가 내보내는 이벤트를 구독하는 별도 컴포넌트로(이벤트가 없으면 이벤트를 추가하는 것이 유일한 Board 수정) ③ 새 블로커·버그 수정만 Board 내부를 건드리며, 그 경우 수정 전 회귀 테스트 세트를 먼저 만든다.

**금지 범위**: TileShader·Radial Warp 셰이더 수정, 매치 판정 알고리즘 재작성(읽기는 가능), Board를 새 클래스로 대체.

## 4. 3단계 구현·테스트 (2주) — 기능 구현 → 테스트

강사 시범은 "코드 변경 0"인 새 레벨 추가로 시작해 데이터·씬·LevelList의 연결을 보여주고, 이어서 팀은 "Board를 건드리지 않고 Board 바깥에서 듣는" 점수 시스템으로 넘어간다. Happy Harvest와 달리 이 게임은 핵심 로직이 한 파일에 집중되어 있어, "건드리지 않는 연습"이 공통 규약보다 중요하다.

**강사 시범 구현 — 새 레벨 「레벨 4」 추가 (약 40분, 라이브)**

1. `feature/level-4` 브랜치 → 레벨 3 씬을 복제해 Level4로 저장, Build Profiles 씬 목록에 추가
2. 레벨 데이터 에셋 복제(또는 Assets > Create > 2D Match) → 젬 종류 수·목표·이동 횟수 변경, 보드 모양에서 칸 몇 개 비우기(보드 모양이 씬의 타일맵인지 데이터인지 0주차에 확정)
3. 블로커 배치를 바꿔 난이도 조정 → LevelList에 등록 → Main 씬에 버튼이 생기는지 확인
4. 플레이 → 커밋 → PR → 학생 리뷰 → 머지
5. 질문: "코드 한 줄 안 고치고 레벨이 늘었다 — 그럼 레벨 디자이너에게 무엇이 더 있으면 좋겠나?" → 레벨 에디터·보드 모양 데이터화 이야기로 연결

**따라야 할 기존 규약 (0주차 정답 분석서에서 확정 후 배포)**

- 네임스페이스 `Match3` 유지, 팀 코드는 `Match3.Team` 같은 하위 네임스페이스와 `Assets/_Team/` 폴더
- Board 내부 상태를 밖에서 직접 읽거나 쓰지 않는다 — 이벤트 또는 공개 읽기 메서드로만. Board에 이벤트를 추가할 때는 기존 이벤트 스타일(C# event / UnityEvent 중 샘플이 쓴 것)을 따른다
- 새 젬·부스터·상점 아이템은 반드시 2D Match 생성 메뉴로 만들고 `Data` 하위 같은 종류 폴더에 둔다
- 레벨 씬은 팀에서 한 사람만 수정. 점수·진행 등 새 컴포넌트는 프리팹으로 만들어 씬에는 프리팹 1개만 놓는다
- 시간·프레임 의존 로직(힌트 타이머, 하트 회복)은 Board의 Update에 끼워 넣지 말고 별도 컴포넌트에서
- 셰이더·매테리얼은 수정 금지. Unity 6 NormalMap 설정 외에는 건드리지 않는다

**테스트 케이스 예시 (양식 D, 점수·별점 기준)**

자동화 시범 대상: 점수 계산(개수·연쇄 → 점수)과 별 판정(남은 이동 → 별 수)을 순수 함수로 분리해 EditMode 테스트 2개. 심화: Board의 매치 판정을 시뮬레이션하는 테스트는 Board가 MonoBehaviour에 묶여 있어 어렵다는 점을 "테스트하기 어려운 설계"의 예로 토론

**시간 함정 (사전 경고)**

- Board.cs 안에서 제거가 일어나는 지점이 하나가 아님 → 점수 이벤트를 한 곳에만 넣으면 부스터 폭발 점수가 빠짐(T-05)
- 레벨 씬 복제 시 Lights 프리팹·카메라 설정이 함께 복사되지만 LevelList 등록을 빼먹으면 레벨이 안 보임 → 체크리스트화
- Unity 6에서 새 매테리얼을 TileShader로 만들면 NormalMap 설정을 다시 해야 함
- 진행 저장(#3)을 PlayerPrefs로 하면 WebGL에서는 브라우저 저장소에 들어가 테스트 시 초기화가 번거로움 → "진행 초기화" 디버그 버튼을 먼저 만들게 함
- 빠른 연속 스와프 시 슬로우모션(포럼 보고) — 학생이 자기 버그로 오해하기 쉬움. 기준 빌드에서 같은 현상이 나는지 먼저 비교하라고 안내

## 5. 4단계 배포 (1주) — WebGL 온라인 배포

《배포 플랫폼》= **WebGL**. 매치-3은 브라우저에서 바로 해보는 장르의 전형이고, 패키지 33MB로 세 게임 중 가장 가볍다. 개발자가 모바일 테스트를 권장할 만큼 모바일 브라우저도 현실적인 목표다(터치 동작은 0주차 확인 결과에 따름).

**빌드 특이사항**

- Sprite Custom Lit·Radial Warp는 일반 스프라이트 셰이더보다 무겁다. WebGL 빌드 후 반짝임·충격파가 보이는지가 첫 확인 항목. Camera Sorting Layer Texture가 일부 모바일 GPU에서 비용이 크므로 필요 시 Radial Warp만 끄는 품질 옵션 제공(선택 과제)
- 세로 화면 게임이므로 WebGL 템플릿 캔버스 비율을 세로(예: 9:16)로 두거나 itch.io 임베드 크기를 맞춘다 — 가로 기본값으로 올리면 보드가 작게 보임
- 텍스처: 젬 스프라이트에 노멀·마스크 맵이 딸려 있으므로 압축 포맷 확인, 스프라이트 아틀라스 유무 확인
- 압축: Brotli + Decompression Fallback
- 입력: 터치가 되면 "모바일 브라우저 지원"을 스토어 페이지에 명시, 안 되면 "PC 전용"
- 진행 저장(#3 구현 팀): WebGL은 브라우저 저장소 — 브라우저를 바꾸면 진행이 사라진다고 페이지에 안내

**목표치 《숫자》** (0주차 강사 빌드 측정값으로 확정): 빌드 폴더 40MB 이하 · 초기 로딩 15초 이내 · 레벨 씬 60fps(PC) / 30fps(모바일 브라우저)

**채널**: 필수 itch.io(세로 임베드 크기 설정 가능, 통계 제공) · 선택 Unity Play 또는 GitHub Pages

**검증 추가 항목** (공통 체크리스트에 더함)

- [ ] Chrome·Edge·Safari에서 젬 반짝임과 매치 충격파가 보이는가
- [ ] 빠른 연속 스와프 10회에도 보드가 멈추지 않는가 (T-07을 빌드에서 재수행)
- [ ] 레벨 실패 → 상점 → 재도전 흐름이 빌드에서 동작하는가
- [ ] (#3 팀) 새로고침 후 클리어한 레벨·별이 유지되는가
- [ ] 스마트폰 브라우저에서 한 레벨 클리어 가능한가 (터치 지원 시)
- [ ] 스토어 페이지에 "Unity Gem Hunter Match 샘플 기반, 추가 기능: …" 와 라이선스 표기

**선택 과제**: 터치·세로 레이아웃(#10) / Radial Warp 품질 토글 / Android 빌드 1회

## 6. 5단계 운영 (0.5주) — 플레이어 유입과 유지보수

매치-3은 "1분 안에 이해되고 한 판이 짧다"는 것이 유입에 유리하지만, 시장에 같은 게임이 수천 개라 "우리 것만의 한 가지"가 없으면 아무도 클릭하지 않는다. 홍보물은 Unity 샘플의 바다 그래픽보다 팀이 추가한 기능(새 블로커·힌트·별점)을 앞에 내세운다.

- **홍보 차별점 《우리가 추가한 기능》**: "얼음 블로커가 있는 레벨 4를 3별로 깨어보세요" 같은 도전 문장 — 매치-3 홍보는 "무엇을 할 수 있나"보다 "얼마나 어렵나"가 클릭을 만든다
- **채널**: 학과 커뮤니티 → itch.io 태그(match-3, puzzle, casual) → 캠주얼 퍼즐 커뮤니티·단톡방 "점수 경쟁" 유도(점수 기능이 있으므로 스크린샷 인증 이벤트가 잘 맞음). 게임잼: 퍼즐 테마 잼 또는 원내 잼
- **기록할 이벤트 3개**: 레벨별 시도·클리어·실패 수(어느 레벨에서 이탈하는가 = 난이도 곡선) / 힌트 사용 횟수 / 상점 구매 횟수. itch.io 통계와 함께 본다
- **피드백 폼 5문항 예시**: 처음 레벨에서 무엇을 해야 하는지 바로 알았나 / 가장 어려웠던 레벨과 이유 / 보드가 멈추거나 이상했던 순간 / 상점을 썼나, 왜 안 썼나 / 있었으면 하는 기능
- **유지보수 고유 점검**: 난이도 조정은 레벨 데이터 에셋(이동 횟수·목표 수·젬 종류 수)만 바꾸면 되므로 핫픽스가 빠름 — "레벨 2가 너무 어렵다" 피드백을 v1.0.1로 당일 반영해 보게 / 보드 멈춤 보고는 재현 절차를 받아 알려진 문제 목록과 대조 / 진행 저장 구조 변경 시 구 저장 데이터 호환
- **후속 경로**: 레벨 10개로 확장해 모바일 빌드 → 학과 전시 / 캡스톤에서 레벨 에디터·리더보드로 이어가기

## 7. 평가 배점, Happy Harvest 과정과의 차이, 출처

공통 루브릭(양식 G)을 기본으로, Gem Hunter Match는 Board 상태 기계 이해가 필수라 분석 배점을 유지하고 배포 배점을 조금 줄인다.

| 항목 | 배점 | Gem Hunter Match 특화 기준 |
| --- | --- | --- |
| 1단계 분석 | 20 | 스와프 1회의 상태 전이도가 맞고, Board 메서드를 6개 구역에 배치했으며, 버그 재현 기록이 있는가 |
| 2단계 설계 | 20 | 기능이 진행 루프(클리어→별→다음 레벨)를 이루는가, Board 수정 범위가 이벤트 추가 수준으로 최소화되었는가 |
| 3단계 구현·테스트 | 35 | 필수 2개 동작 + 회귀(T-04·T-05·T-07) + 부스터 폭발 점수 누락 없음 + 중간 점검 빌드 |
| 4단계 배포 | 15 | 목표치 달성 WebGL + 셰이더 효과 렌더 확인 + 스토어 페이지 |
| 5단계 운영 | 10 | 플레이어 10명 이상 + 레벨별 이탈 데이터 + 난이도 핫픽스 v1.0.1 |

**제출 일정**: Happy Harvest와 동일(1주 분석 → 2주 명세 → 3주 중간 빌드 → 4주 최종 빌드 → 5주 배포 → 6주 운영·발표)

**Happy Harvest 과정과의 차이 (두 게임을 연속으로 가르칠 때)**

| 관점 | Happy Harvest | Gem Hunter Match |
| --- | --- | --- |
| 분석의 핵심 | 타일맵이 곷 상태 — 데이터가 어디 있는가 | Board가 상태 기계 — 상태가 어떻게 바뀜는가 |
| 주 확장 방식 | 새 컴포넌트 + GameManager 필드 | 이벤트 구독 컴포넌트 + 데이터 에셋 |
| 위험 지점 | 실외 씬 병합 충돌 | Board.cs 직접 수정 |
| 고유 학습 포인트 | 상호작용 오브젝트 패턴, 씬 전환과 영속 상태 | 매치-3 알고리즘 읽기, 기존 버그 재현·수정 |
| 학생 체감 난이도 | 낮음(코드 양 적고 분산) | 중간(코드 양 적지만 한 파일이 복잡) |
| 권장 순서 | 먼저 | 나중 — "한 파일을 깊이 읽는" 훈련으로 적합 |

**검토 시 확인 부탁**: `Match3.Board`(Board.cs)·`Gem.cs`·`LevelList`·`Data/BonusItems`·`Data/ShopItems`·`LightRotator`·`TileShader`·`Radial Warp`는 공식 블로그·포럼에 나온 이름이고, 레벨 데이터 에셋·젬 정의·UI 핸들러·인벤토리·진행 저장의 실제 클래스명과 "보드 모양이 씬인가 데이터인가"는 0주차에 프로젝트를 열어 확정해야 한다. Board가 제거 이벤트를 이미 내보내는지도 이때 확인해야 2번 명세서의 "Board 수정 없음" 여부가 정해진다.
