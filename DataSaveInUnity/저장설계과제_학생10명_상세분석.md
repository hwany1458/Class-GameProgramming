## 2. 반 전체에서 관찰된 것

### 2-1. "이벤트"를 읽은 세 층위

과제문의 `이벤트를 기초해서 저장시점을 결정하세요`를 학생들이 서로 다른 깊이로 읽었습니다.

| 층위 | 쓰는 방식 | 학생 |
|---|---|---|
| **1층 — 상태 서술** | "게임이 끝났을 때" / "스테이지를 클리어했을 때". 게임의 상태만 적어, 코드의 어느 지점인지는 알 수 없음. 게임당 저장 시점 보통 1개. | 강보민, 김동현, 김유경, 최민혁(일부) |
| **2층 — 게임 내 사건** | "웨이브 클리어 / 설정 변경 / 강화 구매 / 최고 기록 갱신". 플레이 중 일어나는 일로 분해. 게임당 3~5개로 늘어남. | 김민준, 정종헌, 최민혁, 김주헌, 윤성훈, 이건희 |
| **3층 — 코드 이벤트** | `GameManager.StageClear() → SaveManager.SaveStage()`. 사건을 실제 호출로 특정. | **우왕준 (유일)** |

과제문이 요구한 것은 2층 이상입니다. **1층에 머문 4명은 "저장 시점을 정했다"기보다 "게임이 언제 끝나는지를 적은 것"**에 가깝습니다.

### 2-2. 가장 흔한 오개념 — "저장 시점은 많을수록 좋다"

**김민준**은 저장 시점을 가장 많이(게임당 4~5개) 잡았지만, 그중 두 개가 치명적입니다.

> ① 일반 달걀 또는 황금 달걀을 획득했을 때 → 현재 점수, 획득한 달걀 수, 콤보 수
> ① 적을 처치하여 골드를 획득했을 때 → 보유 골드, 처치한 적의 수

계란 하나, 적 하나마다 디스크에 쓰는 설계입니다. 초당 수십 회 I/O가 발생해 프레임이 끊기고,
PlayerPrefs라면 레지스트리를, 파일이라면 SSD를 계속 두드립니다.
**저장 시점의 수가 아니라, "이 시점에 저장하지 않으면 무엇을 잃는가"가 기준**이어야 합니다.

반대로 같은 안을 **명시적으로 기각한** 학생이 셋 있습니다.

> "먹이를 먹을 때마다 저장하기보다는 게임이 종료되는 시점에 점수를 저장하는 것이 효율적이라고 생각한다." — 정종헌
> "저장하지 않는 시점: 계란이 날아다니는 전투 중, 룰렛이 돌아가는 중." — 이건희
> "떨어지는 계란과 폭탄의 위치를 중간에 저장해도 의미가 없다. 그래서 결과만 저장하고 중간 저장은 하지 않는다." — 윤성훈

### 2-3. 가장 큰 빈틈 — "무엇을 저장하지 않을 것인가"

저장 설계는 포함 목록이 아니라 **경계 결정**입니다. 비저장 항목과 그 근거를 쓴 사람은 4명뿐입니다.

| 학생 | 저장하지 않기로 한 것 | 근거 |
|---|---|---|
| 이건희 | 뱀의 위치·길이, 과일 위치, 타이머 | "판이 끝나면 의미 없음" |
| 윤성훈 | 바구니에만 담고 비우지 않은 계란(`bucketEggs`) | "그래야 '언제 비우러 갈까'라는 판단이 의미 있어진다" ← **게임 디자인과 저장 설계를 연결한 유일한 서술** |
| 정종헌 | 적의 위치·체력 | "해당 웨이브를 처음부터 다시 시작하게 하면 저장 데이터 양을 줄일 수 있다" |
| 김주헌 | 10순위권 밖의 기록 | 랭킹에 쓰지 않으므로 |

### 2-4. 영구(메타) ↔ 진행(런) 데이터 구분

이 구분이 없으면 "게임오버 시 저장"과 "이어하기"가 한 덩어리로 섞여, 실제로 구현할 때 설계가 무너집니다.
용어로 **선언한** 사람은 2명(이건희, 윤성훈), 조건부로 언급한 사람 1명(정종헌)입니다.

> "저장 데이터는 두 종류로 나눈다. (A) 영구 데이터(메타): 판이 끝나도 남아야 하는 것 / (B) 진행 데이터(런): 하던 판을 이어하기 위한 것" — 이건희
> "랭킹, 최고 기록, 이어하기, 설정 → 로컬 JSON 파일" — 윤성훈 (4분류)
> "만약 이어하기 기능을 추가한다면 현재 점수, 뱀의 위치와 이동 방향, 먹이의 위치도 저장해야 한다" — 정종헌

### 2-5. 저장 매체를 정한 사람은 3명

| 학생 | 선택 | 근거 |
|---|---|---|
| 윤성훈 | 로컬 JSON(`Application.persistentDataPath`), 확장 시 PlayFab | **PlayerPrefs를 기각** — "윈도우 레지스트리에 이름=값 쌍으로만 저장되어 랭킹처럼 여러 기록을 구분해 넣기 어렵고, 다른 컴퓨터로 옮길 수도 없다" |
| 이건희 | 게임별로 다르게 — Egg/Snake는 PlayerPrefs(항목이 적고 단순), 디펜스는 `JsonUtility` + `save_slot1.json`, WebGL은 IndexedDB 동기화 | 데이터 양·구조에 따라 선택 |
| 우왕준 | PlayerPrefs (키 이름까지: `EggCatchBest`) | 근거 서술은 없음 |

나머지 7명은 저장 방식을 쓰지 않았습니다. "무엇을 저장할 것인지"의 답이 **데이터 목록에서 멈추고 자료형·저장소까지 가지 않은** 것입니다.

### 2-6. 무결성·악용 방지를 생각한 사람

| 학생 | 쓴 것 |
|---|---|
| 이건희 | **난수 상태(시드) 저장** — "불러온 뒤에도 저장 전과 똑같은 다음 웨이브가 나오도록 (저장/로드를 반복해 좋은 결과를 뽑는 꼼수 방지)" · 전투 중 저장 금지(결과 조작 방지) · **저장 버전 번호**로 구버전 파일 거절/변환 |

### 20252140 윤성훈 — 24/24

**강점**
- **저장 위치를 먼저 정하고 들어감.** 로컬 JSON vs 서버(PlayFab) vs PlayerPrefs를 비교하고, PlayerPrefs를 **이유를 들어 기각**. 과제에서 유일하게 "자기 컴퓨터를 서버로 쓰면 24시간 켜 두기 어렵고 IP가 바뀔 수 있다"까지 따짐.
- 저장 시점에 `a. b. c. d. e.` 라벨을 붙이고 **불러오기 시점(c)까지** 설계 — 저장만 쓰고 로드를 빠뜨린 다른 답안과 구분됨.
- **실제 변수명을 씀**: `barnEggs`, `hit`, `miss`, `bucketEggs`, `coinCount`. 자기 코드를 보면서 쓴 답안.
- **랭킹 정렬 규칙까지 설계**: "barnEggs 높은 순, 같으면 생존 시간 긴 순" / 디펜스는 "승리 기록 먼저, 그 안에서 남은 서버 체력 → 주문 완료 수 순, 실패 기록은 도달 시각 늦은 순".
- **설계 트레이드오프를 명시적으로 처리**: 뱀 게임 모드 조합이 30가지(코인 10 × 속도 3)라 랭킹이 잘게 쪼개지는 문제를 발견하고 "랭킹은 속도 3단계로만 나누고 코인 개수는 표시만" 으로 타협.
- 현재 구현의 결함을 함께 적음 — "지금은 ESC를 누르면 기록 없이 바로 꺼진다".

**보완**
- 저장 데이터의 **자료형**이 없음(int/float/string). 이건희·우왕준이 쓴 수준까지 가면 바로 구현 명세가 됨.
- JSON 스키마 예시(실제 키 구조)가 있으면 완결.
- 저장 실패·파일 손상 시 처리(백업본, 임시 파일 후 교체)가 없음.

- 저장 시점 자체는 **적절합니다.** "스테이지 클리어 시 / 월드 맵 복귀 시 자동 저장"은 디펜스·스테이지형 게임의 표준 해법이고, 전투가 끝나 상태가 안정된 지점을 고른 것도 맞습니다.

**보완 — 재제출 필요**
- **게임 1개만, 그것도 어느 게임인지 쓰지 않았습니다.**
- 저장 대상 `현재 진행도 HP 재화`는 세 단어를 구분자 없이 붙여 쓴 것이고, 각각이 무엇인지(진행도 = 스테이지 번호인지 웨이브인지) 알 수 없습니다.
- 파일명이 `게임의_이해_과제_텍스트`로 되어 있어 **다른 과목 과제와 혼동한 정황**이 있습니다. 확인이 필요합니다.
- 현재 상태로는 과제 요구의 1/6 수준입니다.

## 4. 다음 수업에서 다룰 것 (제안)

제출물에서 **실제로 비어 있던 순서대로**입니다.

1. **영구 데이터 ↔ 진행 데이터** (8명 누락)
   "게임오버 시 저장"과 "이어하기"는 다른 기능이고, 다른 파일에 들어갑니다.
   → 이건희의 `(A) 메타 / (B) 런` 선언을 그대로 보여 주면 한 장으로 끝납니다.

2. **저장 시점은 많을수록 좋은가** (김민준 사례)
   값이 바뀌는 순간 ≠ 저장하는 순간. 메모리 갱신과 영속화를 분리하는 것이 핵심.
   → 반례로 정종헌·윤성훈의 기각 문장을 나란히 제시.

3. **무엇을 저장하지 않을 것인가** (6명 누락)
   → 정종헌("복원하지 않아도 되게 규칙을 바꾼다") vs 이건희("복원해야 하므로 전부 저장한다")를
   같은 문제의 두 해법으로 나란히 놓고 토론시키면 좋은 수업이 됩니다.

4. **저장 매체 선택** (7명 누락)
   PlayerPrefs / JSON + `persistentDataPath` / 서버의 적용 범위.
   → 윤성훈의 PlayerPrefs 기각 근거가 교재 설명보다 명확합니다.

5. **세이브 스커밍과 난수 상태** (1명만)
   → 이건희 사례. 심화로 짧게.

6. **이벤트를 코드 호출로 쓰는 법** (1명만)
   → 우왕준의 `발생 이벤트 / 발생 시점 / 저장 데이터` 3칸 표를 **다음 과제의 제출 양식**으로 지정하면,
   1층에 머문 학생들이 자동으로 2~3층으로 올라갑니다.

### 재제출 권고

| 학생 | 사유 | 보완하면 |
|---|---|---|
| 김동현 | 1개 게임, 4줄 | 과목 혼동 여부 먼저 확인 |
| 김유경 | 1개 게임, 2줄 | 방향은 맞음 — 나머지 2개만 추가 |
| 강보민 | 근거 전무 | 각 항목에 "왜" 한 줄씩 → 15점대 |
| 김주헌 | 내용은 충분, 형식 미달 | 표로 다시 정리 + 지시문 삭제 + 문체 교정 → 18점대 |
